## 第一轮：查看文档和下载原件

现有文件列表提供文件的 `id`。前端用知识库 ID 与文档 ID 请求以下接口：

- `GET /api/knowledge-bases/{kb_id}/documents/{document_id}` 返回当前版本的提取文本和元信息。
- `GET /api/knowledge-bases/{kb_id}/documents/{document_id}/download` 返回导入时保存的原始字节，浏览器按原文件名下载。
- 两个接口都接受 `?version_no=1` 等参数，查询指定历史版本。省略参数时查看当前版本。

详情字段包括 `content`、`version_no`、`sha256`、`imported_at`、`relative_path`、`original_available` 和 `original_size_bytes`。前端可以先用普通文本区域展示 `content`，应通过文本节点渲染用户内容。

`content` 是解析后的文字，下载得到的是原件。Word、Excel 和 PDF 的引用行号对应解析文本。文件归属其他知识库、已删除、指定版本不存在时返回 404。CLI 使用 `--originals skip` 导入的版本仍可读取提取文本，但原件下载返回 404，详情中的原件大小为 null。

前端验收步骤：上传文件，打开详情，下载并比较原件；更新同路径文件后查看第一版与当前版；删除后确认详情与下载均返回 404。

## 第二轮：直接录入一问一答

`POST /api/knowledge-bases/{kb_id}/qa-pairs` 接收以下 JSON，成功返回 201：

```json
{"question":"巡检周期是多久？","answer":"十九天。"}
```

后端生成 `qa/随机编号.txt`，保存成普通知识文档，再沿用既有的分块和检索流程。响应包含 `document_id`、`relative_path`、`status`、`version_no` 和 `searchable`。

保存返回的 `document_id`，以后用 `PUT /api/knowledge-bases/{kb_id}/qa-pairs/{document_id}` 提交同样结构的 JSON 来编辑。相同内容返回 `unchanged`，变化后返回 `updated` 并增加版本号。问题最多 1000 字符，答案最多 10000 字符，去除首尾空白后均不能为空。

问答对会出现在现有文档列表里，能通过文件详情读取，能作为引用来源，也能通过现有 DELETE 文档接口删除。更新接口处理 `qa/` 下的 TXT 条目，普通上传文档请继续使用原上传更新方式。

这是知识录入操作，录入时直接保存人工提供的答案。运行 `/questions` 检查检索无需模型密钥；运行 `/answers` 或 `/answers/stream` 生成回答时仍按原规则调用模型。

前端验收步骤：填写问题和答案后保存，提问确认能检索到；修改答案后确认只使用当前版本；删除后确认检索结果移除该条目。

## 第三轮：保存回答、收集反馈和查看待补充问题

普通 `/answers` 响应和流式 `final` 事件新增 `answer_id`，前端应和本条回答一起保存。原有回答、状态和引用字段保持兼容。

最终答案在发送前写入本机 SQLite，保存当时的问题、收到的三条以内历史问题、最终答案、模型名、引用片段及时间。后续源文件更新或删除时，已保存的引用快照仍可用于复查。流式 `delta` 不写成最终回答；发生模型错误、缺少密钥或请求取消且未形成最终结果时，不创建最终回答记录。

反馈使用 `PUT /api/knowledge-bases/{kb_id}/answers/{answer_id}/feedback`：

```json
{"rating":"unhelpful","comment":"请补充入口和操作步骤"}
```

`rating` 可选 `helpful` 和 `unhelpful`，备注最多 2000 字符，成功返回空 204。重复提交更新同一条反馈。当前每个回答保留一份最新反馈，适用于本地课程演示，尚未区分多个用户的投票。跨知识库提交和不存在的回答返回 404。

`GET /api/knowledge-bases/{kb_id}/answer-records` 返回最近的最终回答及反馈。可以传 `limit`（1～100，默认 20）、`offset`（从 0 开始）分页。设置 `needs_review=true` 后返回资料不足和被标记为 `unhelpful` 的回答，作为补充知识的候选清单。

每条记录包含 `answer_id`、`question`、`history`、`response`、`created_at`、`rating`、`comment`、`feedback_updated_at`。其中 `response` 是原最终回答，含引用。待补充列表中的“未答”指 `insufficient_evidence`，模型调用错误仍按原接口报错处理。

同学可以先接回答下方的反馈按钮，再在管理页增加待补充列表。点击反馈时带回这条回答的 `answer_id`，成功后显示提交状态。尚未接页面时，可以直接在 `/docs` 先做接口验收。

## 怎样理解这三轮的关系

文件导入后，详情接口让管理员看清数据库里存的内容。遇到知识缺口时，管理员可以直接录入问答对。问答过程里的“资料不足”和负面反馈会留在待补充列表里，帮助管理员决定下次补什么资料。

SQLite 新增 `answer_records` 和 `answer_feedback` 两张表。旧数据库在连接时自动补建，原文件、文档版本和检索块沿用原结构。问题与回答保存在本机运行数据库中，该数据库位于 Git 忽略的 `storage/`。
