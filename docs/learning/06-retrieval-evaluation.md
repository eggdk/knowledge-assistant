# 第 6 课：先量出检索错误，再决定怎么优化

我们已经能从本地资料里搜出原文块，但“看起来相关”不等于“找到了回答问题的依据”。这一步给检索器做一场有标准答案的小测验。它不调用大模型，也不评价生成文字的好坏。

## 自己跑一遍

从仓库的 `apps/api` 目录执行：

```powershell
& ..\..\.venv\Scripts\python.exe -m app.evaluation
```

程序每次新建临时 SQLite 数据库，把 `evals/demo/docs/` 里的 **4 篇虚构的“青禾资料站”说明**导入，搜索 `evals/demo/cases.json` 中的 16 道题，结束后删除临时库。这些说明只为演示检索评测而写，不代表我们的项目、课程或 Agent Insight 已实现相应功能。

`cases.json` 放在 `docs/` 外，因此标准答案不会被当成知识库资料导入。12 道可回答题分别标注原文件和答案原文短句；4 道无答案题标注 `source: null`。程序先核验每句标准答案确实完整位于某个当前文本块，然后才计算排名。单纯命中同一个文件的错误段落不算答对。

## 当前基线结果

在 2026-10-27 的演示集上，现有中文双字切分加 BM25 风格排序得到：

| 指标 | 结果 | 意思 |
| --- | ---: | --- |
| 答案原文块 Top-1 | 10/12 | 第一条就包含标注答案 |
| 答案原文块 Top-5 | 12/12 | 前五条至少一条包含标注答案 |
| 无答案题真正无命中 | 0/4 | 四题都搜出了词面相关、但不能回答问题的材料 |

其中 P04 问“哪两种文件”，第一条却是“同名文件更新”；P08 问“谁能撤回”，第一条却是“学生不能撤回”。两题的真正答案都排第 2。当前排序只计算字词重合，不能可靠理解“谁能”和“谁不能”。

无答案题也值得看：停车位问题会碰上“重新申请密码”；微信支付会碰上“支持的格式”；OCR 语言会碰上 PDF 文件说明；链接密码会碰上公开链接说明。这些不是资料中的答案。**不要把 BM25 分数当成正确率，也不要仅凭有命中就生成确定回答。** 以后需要在回答前核实证据是否真的支持结论，无法核实时说明依据不足。

## 我们接下来怎么用它

1. A 岗维护评测程序、标注格式和检索结果；B 岗从实际页面/资料使用情境写自然问题，双方交叉检查“答案原文是否真的支持问题”。
2. 换成真实资料时，复制 `evals/demo/` 作为新评测集，只把允许公开的资料放在 `docs/`，题目和标注仍放在外面的 `cases.json`。使用 `--dataset 你的评测集目录` 运行。私人或未获授权的文档不要提交到公开 GitHub 仓库。
3. 每改一次切块或排序，都记录同一组题的 Top-1、Top-5、无答案误命中数以及具体错误题。开发题可以用来调试；以后再留一组不参与调参的验收题，避免“对着答案改算法”。
4. 这个 16 题集太小、又是人工编写的演示资料，不能据此声称检索质量达到课程验收要求。下一轮要用老师指定的平台资料或团队实际准备的知识库，补充口语问法、错别字、长文跨段、同义词和多轮追问。

查看代码时先读 `app/evaluation.py` 的 `evaluate_dataset`：**导入资料 → 核验标注 → 对每题检索 → 看前五块是否含有答案原文 → 汇总结果**。答案短句只是方便自动打分；最终回答是否正确，仍需人工检查。
