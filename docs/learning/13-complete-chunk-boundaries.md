# 第 13 课：不能把 Trace 切成 ace

更新于 2026-11-10。上次真实回答写出了“ace 实验”，问题来自后端送给模型的原文块：完整原句是“选择已有 Trace 的实验保留当前 Trace，只重试失败评估。”，但旧块从单词中间开始，丢失了前面的限定条件。

## 这次改了什么

旧算法把每块最多限制在 600 个字符，下一块从“上一块末尾减 80”开始，借此重复一点上下文。80 是机械计算的位置，可能落在中文句子或英文单词中间。

现在仍先找这个大致起点，但会向前找附近的换行，尽量保留完整列表项；没找到时再找附近的句末。两者都没有，就尽量避开英文单词内部。块末尾触及字符上限时，也尽量在完整单词前停下。为了避免把重叠扩大得太多，查找范围受到限制。

因此“80 个字符重叠”现在是目标值，不再要求每次恰好 80。超过 600 字符的无分隔长词或长句仍可能需要切开；我们没有承诺任意长内容都能在一个块里完整保留。

原文没有被改写。每个块依然是源文中的连续一段，并带着准确的起止字符位置和行号。现在实际检索到的重试片段从完整的“- 选择已有 Trace……”开始，而不再从“ace”开始。

## 为什么还要更新已导入的知识库

改 Python 代码不会自动改变数据库中已经保存的旧块。新策略因此命名为 `mdtxt-v2`，与旧的 `mdtxt-v1` 区分；旧块继续保留，避免让同一个块 ID 指向不同文字。

新增 `chunks rebuild` 命令，从数据库已保存的当前正文重新切块。它不需要再选原文件，也不需要千问密钥；不会增加文档版本、改原件或覆盖历史。整个知识库的重建在一个事务里完成，任何文档写块失败都会回滚，避免留下半成品。

**A 的本机已完成：**先用 SQLite 备份数据库，再重建现有两个知识库的 5 份资料，得到 208 个 v2 文本块。逐行核对后，原文、原件、文档版本及导入时间保持不变，旧 v1 块也保留。备份位于本机 `storage/knowledge-before-mdtxt-v2-20261110-*.sqlite3`，不上传 GitHub。

**另一台电脑已有旧知识库时：**拉取代码后，在 `apps/api` 目录分别执行下面命令，每条单独按回车。先列库，记下自己的 ID：

```powershell
& ..\..\.venv\Scripts\python.exe -m app.cli kb list
```

再为要使用的库重建，替换 `你的知识库ID`：

```powershell
& ..\..\.venv\Scripts\python.exe -m app.cli chunks rebuild --kb 你的知识库ID
```

重启后端后才能用新代码处理网页提问；A 本机的库已经重建，只需要重启后端并重新提问。其他电脑的数据库不随仓库同步，不能直接照搬 A 的库 ID。尚未重建的旧库在新代码中可能显示 `searchable: false`，因为当前策略尚无块。

## 如何知道没有改坏

- 后端 **88 项通过、1 项跳过**。检查了真实重试句、原文切片、行号、字符上限、不丢非空白字符，以及升级时的回滚、重复执行和不同库隔离。
- Agent Insight 开发集答案块 Top-1 从 **12/18 到 13/18**，Top-5 保持 **17/18**。
- 虚构演示集保持 **10/12、12/12**；三道宽泛问法诊断题保持第 **2、4、1**，都在前五。
- 本机迁移后直接检索“Agent Insight 如何管理实验”，确认候选片段包含完整的重试限定条件。

这些结果证明切块与检索在现有测试上的表现，不代表模型已经重新给出正确答案。本轮没有真实付费调用。下一次网页复测重点看：是否把“选择已有 Trace”与“生成 Trace”这两种实验的重试行为区分清楚，引用是否支持表述。答案里的 Markdown 显示问题仍是单独的前端任务。

代码阅读顺序：`chunking.py` 的 `_choose_overlap_start()` → `split_text_into_chunks()` → `knowledge_store.py` 的 `rebuild_chunks()`。前两个决定怎么切，最后一个负责安全更新旧库。取舍记录见[决策 0008](../decisions/0008-chunk-boundaries-v2.md)。
